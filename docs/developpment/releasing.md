# Releasing

How a version of gatewAI is published, and what each step checks (v4 C.1). The
workflow is `.github/workflows/release.yml`; pushing the tag is the maintainer's
step and the only manual one (agents are denied `git push`).

## What a release is

| Artifact | Where | How to check it |
|---|---|---|
| Multi-arch image (`linux/amd64`, `linux/arm64`) | `ghcr.io/yourimartin/gatewai:<version>`, and `:latest` for a final version | `docker buildx imagetools inspect ghcr.io/yourimartin/gatewai:<version>` |
| Build-provenance attestation (SLSA, Sigstore-signed) | GitHub attestations API, and next to the image | `gh attestation verify oci://ghcr.io/yourimartin/gatewai:<version> --repo YouriMartin/gatewAI` |
| SBOM (SPDX, generated by BuildKit) and BuildKit provenance | inside the image index | `docker buildx imagetools inspect ghcr.io/yourimartin/gatewai:<version> --format '{{json .SBOM}}'` |
| Release notes | GitHub release of the tag | the `CHANGELOG.md` section of that version |

The version is the tag without its `v`. It is passed to Maven as `-Drevision`, so the
jar, the image label `org.opencontainers.image.version` and `build.version` on
`GET /actuator/info` all carry it; nothing released says `SNAPSHOT`.

Verify the **tag** (the index), not a per-architecture manifest: the attestation is
bound to the index digest that the tag points to.

## One-time setup (repository settings)

- **Enable private vulnerability reporting** (*Settings → Code security*):
  `SECURITY.md` and the issue chooser link to it.
- **After the first release, make the package public** (*Packages → gatewai →
  Package settings → Change visibility*). GHCR creates a new package as private,
  whatever the repository's visibility, so until then an anonymous `docker pull`
  fails. The workflow's own jobs log in and are not affected.
- **Protect `main`** with the ruleset kept in the repository,
  [`.github/rulesets/main.json`](../../.github/rulesets/main.json): every change
  arrives by pull request (no approval required — one maintainer cannot approve
  their own), the CI jobs `pinned-actions`, `build`, `integration` and `quickstart`
  must pass, and `main` cannot be force-pushed or deleted. Nobody bypasses it,
  admins included. `integration_id` 15368 is GitHub Actions, so only a check run by
  Actions satisfies a requirement. The weekly CVE scan is left out on purpose: a
  new advisory would block every unrelated merge.
  `gh api -X POST repos/YouriMartin/gatewAI/rulesets --input .github/rulesets/main.json`
  (to change it later: `gh api repos/YouriMartin/gatewAI/rulesets` for its id, then
  `-X PUT …/rulesets/<id>` with the same file).
- **Restrict who can create `v*` tags** (*Settings → Rules → Rulesets*, target: tags
  `v*`, restrict creations to the maintainer). A tag is what triggers a release.

## Cutting a release

1. Make sure CI is green on the `main` commit you are about to tag. The workflow
   refuses a commit that is not on `main`, but it does not rerun the test suite:
   the image build skips tests, as it always has.
2. In `CHANGELOG.md`, rename `## [Unreleased]` to `## [X.Y.Z] - YYYY-MM-DD`, add an
   empty `## [Unreleased]` above it, and commit ("Release X.Y.Z").
3. Tag that commit and push the tag:

   ```bash
   git tag -a vX.Y.Z -m "gatewAI X.Y.Z"
   git push origin vX.Y.Z
   ```

4. Watch the run. On success the image has both tags, the release is published and
   marked latest.

### A test tag

A pre-release (`v0.1.0-rc.1`, any version with a `-` suffix) runs the whole pipeline,
is published as a GitHub *pre-release*, and **never moves `:latest`**. It may go out
on the `[Unreleased]` section, so the changelog does not have to be renamed first.
Use one to check the pipeline end to end before the first real version.

## What the workflow checks, in order

| Job | Fails when | Effect of the failure |
|---|---|---|
| `prepare` | the tag is not `v<semver>`; the commit is not on `main`; `CHANGELOG.md` has no non-empty section for the version (a pre-release falls back to `[Unreleased]`) | nothing built, nothing pushed |
| `image` | the multi-arch build fails | nothing pushed |
| `smoke` (amd64, arm64) | on either architecture: the container is not the expected architecture, is not healthy within 10 min, reports another `build.version`, or does not answer a chat completion | the image exists by digest only — **no tag points at it** |
| `publish` | the attestation does not verify; the tag does not resolve to the tested digest | no tag, or a tag but no release |

The image is pushed **by digest, untagged**, booted on both architectures, and only
then tagged. A failed run therefore leaves an untagged digest in the package (delete
it from the package page if you want) and never a pullable broken `:<version>`.

`smoke` runs `scripts/image-smoke.sh`, which works the same locally:

```bash
docker build -t gatewai:local --build-arg GATEWAI_VERSION=0.0.0-local .
EXPECTED_VERSION=0.0.0-local scripts/image-smoke.sh gatewai:local
scripts/image-smoke.sh ghcr.io/yourimartin/gatewai:X.Y.Z linux/arm64   # needs arm64 or binfmt
```

Each architecture is tested on its own hardware (`ubuntu-24.04` and
`ubuntu-24.04-arm`), because ONNX Runtime and the DJL tokenizer each load a native
library per architecture at startup: an image that only booted on amd64 says nothing
about arm64.

## Why the workflows are pinned

Every `uses:` names a full commit SHA with the version in a trailing comment, and
`scripts/check-pinned-actions.sh` fails CI on any that does not (the `pinned-actions`
job). The helper images the release builds with — BuildKit, the QEMU `binfmt`
installer, the Dockerfile frontend, the two `eclipse-temurin` bases — are pinned by
digest for the same reason. Dependabot proposes the updates weekly, after a 7-day
cooldown. The rationale and its source: [`../technical/security.md`](../technical/security.md#supply-chain-ci-and-releases).
